# Перенос разработки в новый чат (с подключённым git-форком)

Цель: новый чат получает **всю** нужную контекстную базу через сам репозиторий
(дизайн-документ + черновик кода живут в ветке), а не через пересказ в чате.
Контекст, который живёт только в этом чате, — в разделе 4 (handoff-промпт).

---

## 1. Подготовка на GitHub (10 минут)

1. **Форк**: [github.com/jrush64/MassEffect1-VR](https://github.com/jrush64/MassEffect1-VR)
   → кнопка **Fork** → в ваш аккаунт.
2. **Ветка**: в форке создайте ветку `stage1-controller-input` из `main`.
3. **Коммит артефактов** в ветку (файлы из каталога `mele-vr-stage1/` этого
   рабочего пространства):

   ```
   docs/STAGE1_CONTROLLER_DESIGN.md   <- STAGE1_DESIGN.md (дизайн-документ)
   stage1/xr_input.h                  <- code/xr_input.h
   stage1/xr_input.cpp                <- code/xr_input.cpp
   stage1/patches/01_xr_types.h.txt   <- code/patches/... (все 5 файлов)
   stage1/patches/02_xr_session.cpp.txt
   stage1/patches/03_vr_menu.cpp.txt
   stage1/patches/04_vr_config.txt
   stage1/patches/05_vcxproj.txt
   ```

   Коммит с сообщением, например:
   `stage1: controller input design + code draft (not yet integrated)`

4. (Опционально) **PR** `stage1-controller-input` → в ваш же `main` форка:
   удобный хранилище для инкрементальных коммитов (M0/M1/M2/M3).

## 2. Новый чат в Arena

1. Откройте новый чат.
2. Подключите приложение **GitHub** (коннектор) — авторизуйтесь аккаунтом,
   где лежит ваш форк.
3. Первая реплика — **handoff-промпт** из раздела 3 (скопируйте целиком,
   подставьте ссылку на ваш форк).
4. Дальше агент сам: загрузит инструменты коннектора, прочитает
   `docs/STAGE1_CONTROLLER_DESIGN.md` и `stage1/` из вашей ветки.

## 3. Handoff-промпт (первая реплика в новом чате)

> Продолжаем разработку VR-мода для Mass Effect 1 (форк `jrush64/MassEffect1-VR`;
> мой форк: <ССЫЛКА НА ВАШ ФОРК>, ветка `stage1-controller-input`).
>
> **Что это за проект (коротко):** `dxgi.dll`-прокси для Mass Effect Legendary
> Edition (UE3, build 2.0.0.48602) — хуки D3D11 + UE3 render path, вывод в любой
> OpenXR-рантайм (SteamVR/Quest Link). ~31k строк C++, компиляция только на
> Windows (Visual Studio 2022, `scripts\build.bat`). **OpenXR-SDK в проекте НЕТ**:
> все OpenXR-типы hand-written в `src/xr_types.h` (ABI-критично!), функции
> резолвятся из `openxr_loader.dll` через `xrGetInstanceProcAddr`. Всё работает
> на render-потоке игры. Записи в память игры — только через «санкционированный»
> путь `HeadAim::EnsureController/ControllerStable` + SEH + карантин 90 кадров.
> Лог — `MELEVR_Log.txt` рядом с игрой. Лицензия GPL-3.0.
>
> **Задача:** реализовать Этап 1 — управление оружием с VR-контроллеров
> (прицел лучом правого контроллера + «виртуальный XInput-геймпад»: триггер =
> выстрел, стики/кнопки = движение/способности). Механика «как в HL2», визуал
> рук/привязки оружия — за рамками Этапа 1.
>
> **Где всё описано (читать в этой последовательности):**
> 1. `docs/STAGE1_CONTROLLER_DESIGN.md` — дизайн, карта изменений по файлам,
>    ABI-проверка (раздел 9), тест-план (раздел 11), вехи (раздел 12),
>    0.9-фолбэк (Приложение А).
> 2. `stage1/xr_input.h` + `stage1/xr_input.cpp` — черновик нового модуля
>    `MELEVR::XrInput` (самодостаточен, fail-safe).
> 3. `stage1/patches/*.txt` — точные вставки в существующие файлы с якорями
>    (по строкам `src/xr_session.cpp`, `src/vr_menu.cpp`, `src/vr_config.*`).
>
> **Ключевые ограничения (не нарушать):**
> - Все новые настройки — OFF по умолчанию; любой сбой OpenXR → поведение
>   идентично текущему (реальный геймпад passthrough + head aim).
> - Новых записей в память игры НЕТ: aim пишется существующим
>   `DriveAimWithHead(yaw,pitch)` — меняется только источник углов.
> - ABI OpenXR: константы/лейауты в разделе 9 дизайн-дока зафиксированы из
>   Khronos-хедера, но бандл-лоадер может быть 0.9-эры — в `XrInput::Init()`
>   уже есть ABI-проба с логом; первый запуск решит, нужен ли 0.9-фолбэк
>   (Приложение А).
> - Стилистика: `MELEVR::Xr` для типов, `LogLine` для логов, паттерн
>   `ResetBtn` в меню, ключи ini — snake_case-имена по образцу существующих.
>
> **Ограничение среды:** в песочнице нет Windows-тулчейна — сборка и тест
> запускаются у меня на машине (VS2022 + SteamVR). Я приношу сюда фрагменты
> `MELEVR_Log.txt` и скриншоты, ты готовишь код и патчи.
>
> **Первый шаг:** проревью черновик и патчи, укажи проблемы, затем начни
> интеграцию M0: типы в `xr_types.h` (патч 01), 7 ключей конфига (патч 04),
> скелет секции меню (патч 03B) — чтобы первый запуск выдал результат ABI-пробы.

## 4. Что НЕ передаётся автоматически (уже в промпте, но имейте в виду)

- **Решения, принятые в этом чате**: почему tracking через action spaces, а не
  через input spaces (бандл-лоадер имеет 4-полевой 0.9-`XrReferenceSpaceCreateInfo`);
  почему view при controller aim остаётся head-stable; почему fire бинарный.
  Всё это записано в дизайн-доке (разделы 4.2, 5, 6) — промпт ссылается на него.
- **Сверка с реальным кодом** уже сделана: якоря в патчах даны по реальным строкам
  (фрейм-луп: `waitFrame` 3443 → `LocateHead` 3790 → `headQuatForFrame` 3828 →
  weapon-mode 3935; on-foot aim ~4010; Мако ~3895; XInput-хуки ~180/207;
  конфиг-диспетчер ~239/248; save ~472).
- **Открытые вопросы** (зафиксированы в дизайн-доке, не «в голове»):
  - поколение ABI бандл-лоадера (решается на M0-запуске);
  - точный маппинг кнопок ME1 на XInput (решается на T4, `controllerLogRealPad`);
  - TODO в патче (C): вынести explore head-look expression в хелпер для
    head-stable view при controller aim.

## 5. Рабочий цикл после переноса

```
новый чат готовит коммит (M0/M1/M2/M3)
      ↓
вы: git pull → scripts\build.bat → запуск игры (+шлем по мере вех)
      ↓
вы: копировать в чат фрагменты MELEVR_Log.txt
    (для M0 — обязательно строки "[XRINPUT]"; для T4 — "[PADMAP]")
      ↓
новый чат фиксирует ABI / правит маппинг / следующий коммит
```

Полезно пересылать в чат конкретные метки логов, а не весь файл:
`[XRINPUT]`, `[PADMAP]`, `[HEADAIM]`, `[MAKOAIM]`.

## 6. Если форк не создали / GitHub не подключается

Альтернатива (хуже, но работает): приложите к первой реплике в новом чате
архив `mele-vr-stage1.zip` из этого рабочего пространства + скиньте ссылку на
оригинальный репозиторий. Тогда новый чат сможет читать оригинал по web, но
писать будет только в «воздушный» проект — поэтому git-форк всё-таки предпочтительнее.
